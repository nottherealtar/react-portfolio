Your coding agent's sandbox is off. Here's how to turn it on without breaking everything.

After an hour you either turn the sandbox off or add broad rules ("allow all of ~") that quietly undo it. The agent wrote files that a trusted tool outside the sandbox later acted on: hook configs, IDE task files, git metadata. That is the important lesson for anyone configuring a sandbox: the dangerous permission isn't "write anywhere", it's "write to a file something else will execute later".

Every major coding agent now ships a sandbox. Claude Code has /sandbox , Codex has workspace-write , and there's Anthropic's open-source sandbox-runtime, nono and others. They all work the same way: deny everything, then allow what you list.

And that is exactly why most people don't use them. A deny-by-default sandbox asks you a question you can't answer up front: which websites and folders does my work need? So you switch it on and find out the hard way.

Claude Code saves a transcript of every session in ~/.claude/projects , and Codex does the same in ~/.codex/sessions . A transcript shows npm install , not that npm talked to registry.npmjs.org and wrote to ~/.npm . Turning commands into needs takes three things: A real shell parser.

Agents write scripts: cd web && npm ci && npm run build 2>&1 | tail . You need pipes, lists, cd tracking, redirects, heredocs, bash -c "…" , and wrappers like sudo , env , timeout , xargs , npx and python -m . Knowledge of what tools do behind the scenes.

Which hosts cargo build reaches, where uv keeps its cache, which pnpm subcommands start a server. Generalize a write to the cache folder, never to your home folder. Treat tools that need your credentials ( gh , docker , git push over SSH) as "run outside the sandbox", not "punch a hole in it".

The most useful thing a tool like this can do is tell you what will break before you change anything. sandfit replays your history against the sandbox you have today, and against the policy it proposes. To keep that number honest, it builds the policy from your older history and tests it on your newest 20%, which it never looked at.

A policy that only fits the data it was built from is easy; one that works on next week's commands is the point.
