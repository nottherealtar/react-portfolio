A Simulation ID Is Not a Running Simulation

MiroFish answered that the simulation had not been prepared. A typed client can still encode the wrong lifecycle I started with the reasonable model: upload context, ask MiroFish to build a graph, start a simulation, then fetch its report. Graph construction did return a task ID and required polling.

Key details from the source

Editorial digest: additional context drawn from the original reporting. Open the primary source for quotes, figures, and updates.

That was the sixth version of the gateway's live MiroFish path. Five earlier runs had already found a wrong Redis instance, a duplicate simulation record, a synchronous ontology response mistaken for an asynchronous task, a project ID nested under data , and graph status nested under the same wrapper. The seventh run added preparation and exposed one final missing operation: report generation had to be triggered explicitly after the swarm stopped.

None of those failures required a clever algorithm. They required the client to admit that the upstream API was a state machine, even though its surface looked like a collection of ordinary HTTP calls. Each response could be assigned a TypeScript type.

The live service returned the ontology synchronously and placed the project ID inside a { data, success } envelope. Two adjacent operations used different completion models. Then the graph-status response used another nested payload.

The initial poller read status at the top level, so it kept waiting even after the service had completed the job. That is a dangerous integration failure because nothing crashes. The worker appears busy until its timeout expires.

TypeScript helped once those facts were known. It could not discover them from an API that returned HTTP success for an operation whose downstream state was not ready. Live execution supplied the missing contract.

The response normalizers now stay close to the operations they describe. Profile payloads, action logs, graph data, task status, and report state do not pass through one catch-all decoder. Each normalizer accepts the wrapper shapes observed for that operation and rejects data that cannot produce its domain type.

That creates more small functions than one generic unwrapData() helper. A universal unwrapping function would tell the caller that a payload exists, while concealing whether it contains project_id , simulation_id , task_id , or runner_status . The client needs those distinctions to decide what can happen next.

The live failures also changed the test boundary. Unit tests cover the client methods and poll behavior, but recorded response shapes are only hypotheses until a real MiroFish checkout answers. The launch run became a contract test for the whole lifecycle.

Why this matters

Five earlier runs had already found a wrong Redis instance, a duplicate simulation record, a synchronous ontology response mistaken for an asynchronous task, a project ID nested under data , and graph status nested under the same wrapper. It highlights where brittle integrations become operational debt as vendors iterate quickly.

Operational takeaways

  • I expected a task ID and wrote polling logic around it.
  • The gateway had to create a simulation, retain the returned simulation ID, prepare profiles and configuration, wait for preparation, then start the run.
  • Inventory dependent integrations and add regression checks before you widen rollout.
