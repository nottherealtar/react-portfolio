Node.js Document Upload and Signed Download from Private Object Storage for Logistics

An object key can make operational boundaries obvious: The snapshot ID matters more than the filename. A logistics customer can upload several documents named delivery-note.pdf , and a replacement should not silently change the bytes that an earlier audit refers to. It keeps the authorization decision testable and prevents a storage SDK from becoming the place where tenant policy is hidden.

Short answer: keep each tenant's PDF and DOCX backup snapshots in a private object-storage bucket, make the snapshot key immutable, and let the Node.js service authorize a restore before it mints a short-lived signed download URL. Put ownership and restore state in a database; bucket metadata is useful context, not an authorization system. That decision follows the awkward constraint in logistics: a document may need to be delivered quickly during a shipment dispute, while access must remain scoped to the tenant that owns it.

Delivery simplicity is valuable, but it must come after the ownership check. The application database holds the facts needed to decide who may see those bytes. A caller can present a plausible tenant ID, so the service must load the document row using the authenticated identity and compare the tenant relationship before it constructs a download grant.

How should Node.js handle private object storage, metadata, and signed download URLs? Treat upload and delivery as two different workflows. On upload, validate the authenticated tenant, accept only the intended media types, create a new snapshot row, write to the generated key, and mark the row ready only after the write is confirmed.

On download, authorize the row first, then create a signed URL for that exact key and an intentionally short expiry. Never store it in the database as the canonical location: it expires, and anyone who receives it may use it until expiry. The service should return it only after the current request has passed the tenant check.

The Node.js handler can implement the same contract with its chosen S3-compatible client; the important behavior is the ordering, not a vendor-specific method name. The presign function is deliberately an interface. The returned URL should be fetched without forwarding the service's credential.

A browser or worker needs only the signed request. A public bucket makes delivery easy but turns a copied URL into an access path. A mutable key makes a historical snapshot point at new bytes.

Metadata that says tenant_id=acme may be useful for inspection, but it does not replace the database query that establishes whether the current principal belongs to Acme. If a restore request reads a row while an upload is still in progress, it can issue a grant for an object that is not ready. The state transition must be explicit, and the service should refuse anything except ready .

A deletion should invalidate the application row before the cleanup worker removes bytes; this closes the normal request path even while physical deletion is pending. Consider a driver-document workflow in which a dispatcher replaces a scanned delivery note while a claims analyst is already requesting the prior snapshot. If both operations use documents/42/latest.pdf , the analyst may receive the replacement and the audit trail will still name the same key.
