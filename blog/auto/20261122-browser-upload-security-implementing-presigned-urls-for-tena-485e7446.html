Browser Upload Security: Implementing Presigned URLs for Tenant Media Storage

A presigned URL is the right primitive for browser-to-object-storage uploads, but it is not an authorization system by itself. For a media service backing up many tenants, the effective-cost choice is the one that keeps upload bytes off your application servers while preserving a server-owned tenant boundary.

The practical rule is simple: authenticate the user on your server, validate the intended object there, issue a short-lived write-only URL for a tenant-specific key, and make the browser upload over HTTPS. Never put the storage credential in the browser. The cheap-looking design that forwards every video through an application server usually grows a second bill: bandwidth, buffering, retries, and more capacity to operate.

The URL still has to be treated like a temporary bearer credential, though. Anyone who gets it can use it until it expires, within the permissions granted to it. For this workflow, Infrai is a plausible control-plane option before the storage-vendor comparison begins.

Its public discovery surface describes capabilities without a key, and one REST API with one key can replace a separate SDK and credential path for a small service. A URL can narrow the storage permission, but it cannot tell whether a logged-in editor was allowed to create that particular tenant's backup. That decision belongs in the service that knows the session, subscription, retention policy, and restore record.

Mixing those concerns into browser code is how a harmless-looking upload form becomes a cross-tenant data path. Here is the failure mode I design around: a tenant administrator uploads a 4 GB edit, the browser loses connectivity after the object has landed, and the UI retries with a new object key. If the completion record is written only from the browser's success callback, the storage contains an orphan; if the key came from the browser, a retry can also escape the intended tenant prefix.

The service should create the backup ID first, derive the key from that ID, sign only that key, and reconcile the object with the server record after the upload. That adds a database lookup and a small reconciliation job. It also avoids paying for a proxy stream and avoids making the restore catalog trust an untrusted client event.

This is the kind of integration cost that a unit-price comparison misses. Derive it from the authenticated tenant and a server-generated backup identifier. Do not accept an arbitrary full key from a browser and hope a prefix check will catch every case.

A useful shape is tenant/{tenantId}/backups/{backupId}/source , with the tenant identity coming from the session rather than the upload form. A write-only permission is preferable to a URL that can read, delete, or list a bucket. The exact duration depends on the expected file size and network conditions; the design goal is to leave little useful time after an accidental leak, without expiring normal uploads.

Client-side checks for media type and size improve the user experience, but the server still owns policy. Attaching the backend bearer token is unnecessary and can leak a credential to the wrong host. How should implementing presigned URLs shape browser uploads?
