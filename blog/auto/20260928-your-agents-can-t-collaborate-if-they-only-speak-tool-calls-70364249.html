Your agents can’t collaborate if they only speak tool calls — the A2A protocol that fixes peer handoffs — A2A Under the Linux Foundation

You build your first agents, you wire them together with tool calls, and it works. When my billing agent needed the refund agent to decide something—not fetch a value, not execute a command, but reason through policy and arrive at a judgment—that was never an MCP-shaped problem. And horizontal problems need a different protocol.

Key details from the source

I spent three weeks trying to make a billing agent ask a refund agent a question. That was the day I stopped treating agents like functions. It needs to decide the request is out of scope and say no.

But your architecture treats it as a passive function, so every one of those behaviors looks like a failure—a timeout, a malformed response, an unhandled edge case. I had confused the vertical with the horizontal. Before it, connecting five agents to ten tools meant up to fifty bespoke integrations, each one a maintenance liability.

By mid-2025, the community had built thousands of active MCP servers, and OpenAI, Microsoft, and Google DeepMind all adopted it. But MCP has no concept of a peer agent with its own goals, its own model, and its own authority to act. An MCP server that wraps kubectl does not think, negotiate, or push back.

The agent stays in charge; the things it touches are passive. And horizontal problems need a different protocol. The Agent2Agent (A2A) protocol is an open standard launched by Google in April 2025 and now governed by the Linux Foundation's Agentic AI Foundation.

Where MCP is the vertical integration layer connecting agents to internal tools and databases, A2A acts as the horizontal protocol enabling peer-to-peer collaboration. The A2A specification puts the distinction in one sentence: MCP standardizes how an agent uses a tool or resource; A2A standardizes how one agent delegates work to another . Just as HTTP enables any web browser to communicate with any web server regardless of their underlying technologies, A2A enables a LangGraph agent to delegate work to a CrewAI agent, which can…

The architectural shift matters because it changes what the calling agent expects. When you call an API, it simply returns data or fails. The receiving agent can understand intent, refine the plan, push back on incomplete requests, and ask clarifying questions if something is off.

Under the Hood: Agent Cards and Task Lifecycle A2A standardizes four objects: an Agent Card, a Task, a Message, and an Artifact. The Agent Card is a JSON manifest served at a well-known URI, describing who an agent is, what it can do, where to reach it, and how to authenticate. It queries the registry, reads the card, and decides whether to delegate.

The Task is the unit of work, with an ID, a context ID, a state, a history, and artifacts. Tasks are stateful and progress through a defined lifecycle: submitted, working, input-required, completed, failed, canceled, rejected. The input-required state is the one that matters most in practice—it's the protocol's way of letting a receiving agent ask a clarifying question without collapsing the whole interaction.

Why this matters

The billing agent needed to know whether a refund was appropriate, and the refund agent needed to reason about policy, check account history, and possibly refuse. It is a useful datapoint for how AI-assisted engineering and operations are converging in production. It highlights where brittle integrations become operational debt as vendors iterate quickly.

Operational takeaways

  • Where MCP is the vertical integration layer connecting agents to internal tools and databases, A2A acts as the horizontal protocol enabling peer-to-peer collaboration.
  • The receiving agent can understand intent, refine the plan, push back on incomplete requests, and ask clarifying questions if something is off.
  • That's not a tool call.
