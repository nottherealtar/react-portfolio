Cutting pull request review time with AI: GitLab, Azure Repos, Bitbucket

Bitbucket Data Center has no native AI reviewer at all, so review time is set by merge checks and whatever bot you wire in through the REST API. A reviewer with no scoping reviews lock files and generated code forever. GitLab: two review features, two add-on paths GitLab runs one of two code review features depending on your add-on and group settings.

Key details from the source

Editorial digest: additional context drawn from the original reporting. Open the primary source for quotes, figures, and updates.

It is about six configuration decisions, and each of the three forges on this beat implements them differently. On GitLab both code review features run on GitLab.com, Self-Managed and Dedicated, but they are gated by different add-ons. On Azure Repos Copilot code review runs on Services only, in limited preview, and requires Azure Pipelines.

When the review starts, which files it reads, whether it runs on a draft, whether a finding actually blocks the merge, whether a new push triggers a new review, and how much effort each review is allowed to spend. Below is what each forge documents for those six, and where the defaults work against you. The six levers that set review latency An AI reviewer adds a step to a workflow that already has a human bottleneck, so the useful question is whether it removes more waiting than it adds.

That depends on these: Trigger : on every push, on PR creation, or only when someone asks. Scope : which files get reviewed and which are skipped, including how large diffs are handled. Draft behavior : whether a review runs, or a gate silently disappears, before the PR is marked ready.

Blocking : whether a finding stops the merge or is only a comment. Re-review : whether new commits get a fresh review and whether the bot remembers what it already said. Effort and cost : how much the reviewer is allowed to think, and who pays for it.

Those six are also where most "we turned on AI review and nothing got faster" reports come from. A review that runs but does not block anything is a comment feed. A gate that disappears on drafts is not a gate.

If that user holds a Duo Enterprise seat, GitLab runs the non-agentic feature by default, because it does not consume GitLab Credits. Both features can run in the same project, which is worth knowing before you assume everyone on the team gets the same reviewer. The self-managed detail that decides whether any of this is usable: Code Review Flow runs as a CI/CD job and needs a runner with the gitlab--duo tag and an executor that supports Docker images, or GitLab hosted runners enabled for the project.

On an air-gapped instance with no such runner, the flow has nowhere to execute. The non-agentic feature does not have that requirement, but it does depend on the AI Gateway request timeout, and reviews that do not finish in that window surface as a generic error. For triggering, automatic reviews are a project setting since 18.0.

Group and instance level automatic reviews arrived in 18.4 behind the cascading_auto_duo_code_review_settings flag, which was removed in 18.7. Code Review Flow also has a Start a new review on push option, and its follow-up reviews use earlier Duo threads and replies to judge the new changes. A user's request for changes blocks a merge on Premium and Ultimate, and a bot can bypass it.

Why this matters

On GitLab both code review features run on GitLab.com, Self-Managed and Dedicated, but they are gated by different add-ons. It is a useful datapoint for how AI-assisted engineering and operations are converging in production. It highlights where brittle integrations become operational debt as vendors iterate quickly.
