A request to modernize an application often starts with a technology question: Which framework should replace the old one? Before you choose, find out what still works. Then collect evidence that can act as a regression net for that behavior and show where modernization is necessary.

I used an evidence-first method on four public applications, from a small Node.js game to a large Java enterprise resource planning (ERP) application. Each needed a different treatment, but the way I collected evidence, chose the next experiment, and decided on possible proof points was repeatable. This post walks through that process so you can apply it to one application of your own.

It also shows how to encode the procedure in a GitHub Copilot agent skill while keeping architectural judgment with the people responsible for the system. Build evidence before choosing a target The label on an application rarely tells you enough. “Java microservices” doesn’t tell you which Java Development Kit (JDK) runs in production, where that version is pinned, whether the tests execute, or which interfaces other systems depend on.

“Legacy monolith” doesn’t tell you whether the business core is broken or whether one retired platform dependency prevents the application from starting. I use three simple labels: documented, inferred, and unverified. If two files disagree about the Java version, resolve the contradiction.

If you can’t determine whether a CI check blocks merges, say so. Record the unknown rather than treating a guess as a finding. That inventory gives you something concrete to review with the people who own the application before you propose changes.

Choose the least disruptive treatment that works Once you understand the application, make the decision per component. A single system can contain code that should stay, dependencies that should be swapped, and one subsystem that genuinely needs a rewrite. First, check whether a capability is still needed.

Remove it only after verifying that it is unused or superseded and confirming that decision with its owner. Removal is a separate decision, and it’s not necessarily the most disruptive one. For a capability you still need, start with the option that changes the least: Keep it.

Supported code that still fits the job doesn’t need a modernization story. Move to a supported major version and fix the breaking changes. Replace an abandoned dependency while preserving the existing design.

Why this matters

Supported code that still fits the job doesn’t need a modernization story. It reframes risk for teams that automate sensitive workflows and rely on third-party data flows. It is a useful datapoint for how AI-assisted engineering and operations are converging in production.

Operational takeaways

  • Build evidence before choosing a target The label on an application rarely tells you enough.
  • For a capability you still need, start with the option that changes the least: Keep it.
  • Replace an abandoned dependency while preserving the existing design.
