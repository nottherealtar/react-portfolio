Dispatches from O'Reilly: The right amount of spec for agentic development

In the agent world, vague requirements run into machine speed. That’s why specification suddenly feels important again. But the real problem lives upstream, in the spec, so fixing it means unwinding code and reasoning together.

Key details from the source

Editorial digest: additional context drawn from the original reporting. Open the primary source for quotes, figures, and updates.

I keep seeing the same idea in conversations about agents: Detailed specs are old-world overhead now. Give the model a rough goal, let it explore, fix what comes back, move on. It sounds efficient but it also hides the cost.

A simple prompt looks cheap and tempting because it gets implementation started right away. You review output, clarify intent, ask for changes, rerun tests, find the next gap, and do it again. Someone still has to decide whether the result matches the real goal.

At the other extreme, full formal specification is obviously expensive up front. Writing acceptance criteria, contract tests, or behavior-driven development (BDD) scenarios takes real effort. But the downstream cost is different because more of the oracle is executable.

A test checks the same condition every time. It doesn’t get tired, rushed, or optimistic five minutes before lunch. The question is not whether specification is good or bad.

For most agentic work, it’s somewhere in the middle: enough structure to constrain the work, enough examples to make intent concrete, and enough executable checks that review does not turn into guessing. Zero spec is not intelligent and lean; it’s just costly vibe-coding. Software engineering was never mainly about typing or even producing code.

It was about deciding what should exist, what should never happen, which trade-offs matter, and what “done” means once the problem touches the real world. For years, teams discovered missing specification through human friction. A reviewer noticed an edge case, QA found the path nobody described, a senior engineer carried half the real requirements in his head and translated them one meeting at a time.

None of that was elegant, but it did force ambiguity into the open. They make implementation much cheaper and much faster. It also means an underspecified idea can turn into a plausible system before anyone has really agreed on what the system is supposed to mean.

We just used implementation cost as a crude forcing function and called the result process. This is the part I see people skip most often. They talk as if the sequence is simple: write the spec, then let the agent implement it.

Why this matters

I keep seeing the same idea in conversations about agents: Detailed specs are old-world overhead now. It reframes risk for teams that automate sensitive workflows and rely on third-party data flows. It highlights where brittle integrations become operational debt as vendors iterate quickly.

Operational takeaways

  • At the other extreme, full formal specification is obviously expensive up front.
  • When an agent executes a flawed spec faithfully, the failure gets harder to diagnose.
  • The implementation may look coherent.
