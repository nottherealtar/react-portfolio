Staying Evergreen: How we automated secure access and repo hygiene in a shared org

To keep up, repository owners need to track collaborators, deadlines, and follow-ups for each repository. Evergreen is a GitHub App that automates organization hygiene through two workflows: Outside collaborator access reviews. Otherwise, look at recent issue and commit authors and cc the ones who are on the access review team, i.e., the Hubbers actually working in that repo.

You need to confirm who still needs access, change permissions as projects evolve, and archive repositories once they’ve served their purpose. As a project grows, that manual housekeeping becomes harder to keep up with and easier to defer. We faced this problem in a shared organization where GitHub employees (“Hubbers”) collaborate with customers and partners on product trials and professional services engagements.

Our answer was Evergreen , a GitHub App built with native GitHub features. The workflows below exhibit a pattern you can adapt for your own organization. Repos with no human activity past a threshold get flagged, warned, and (if still untouched) archived.

Two design principles shaped everything: Fail secure. If nobody responds to an access review, we don’t leave access in place and hope for the best. Evergreen will never delete a repository or its contents.

Archived repos are recoverable, and every access change is written into the repo’s tracking issue, so reverting a mistake is as easy as a copy-paste to Copilot. Under the hood, Evergreen is a small Go webhook server running in a container. But the interesting part is the choreography .

Every moving piece is a stock GitHub feature: a GitHub App, scheduled actions, webhooks, issues, custom properties, and plain files in a repo. A dedicated controller repo acts as Evergreen’s clock and its memory. Four scheduled GitHub Actions workflows fire repository_dispatch events on a quarterly cadence, and the app wakes up and does the work: Reviews open two weeks before their cleanup runs, and there’s a hard grace period baked in so a stray manual run can never fast‑forward the guillotine.

Each workflow also supports workflow_dispatch , so we can trigger any step by hand as needed. Evergreen tracks every repo’s status as a JSON file (one per repository) committed to the controller repo under state/repos/<repo_id>.json . The snapshot of who had access, when the review opened, the deadline, who decided, and what happened all lives there.

Here’s a completed review where a Hubber kept Alice’s access and let Bob’s lapse: The best part: because state is just files in git, the commit history is the audit trail. Want to know why someone lost access last spring? There’s no separate database or bespoke audit pipeline to track.

When an access review kicks off, every repo gets a checklist issue: The interaction model is delightfully simple: check the boxes for who stays, then close the issue. When the issue closes, Evergreen listens for the issues.closed webhook event, reads the checkboxes, retains the checked collaborators, and revokes the rest, then posts a receipt comment listing exactly what it kept and what it removed. Only the right humans can pull the lever Closing an access review issue is a privileged action, so Evergreen guards it.
