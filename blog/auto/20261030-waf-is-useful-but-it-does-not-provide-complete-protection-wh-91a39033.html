A Checkpoint for Incoming Web Traffic A WAF (Web Application Firewall) is a security function that inspects HTTP/HTTPS traffic reaching websites and Web APIs. It applies predefined rules to decide whether to allow, log, or block that traffic. A useful way to understand it is as a checkpoint placed in front of a website.

There Are Boundaries to What a WAF Can Protect Because a WAF operates at the entry point for web traffic, it can be effective against attacks that can be identified from the contents of that traffic. However, determining whether an application's internal processing is correct, whether a logged-in user is entitled to access particular data, or whether a server or middleware component has an underlying weakness is not the WAF's role. Virtual Patching Is Not a Substitute for a Permanent Fix This does not mean that a WAF can never…

This approach is known as virtual patching . However, virtual patching does not fix vulnerable code. It is effective only against attack patterns that the WAF can recognize in traffic it inspects.

If an attacker changes the attack method or input format, or uses a route that bypasses the WAF, the protection may no longer apply. OWASP also explains that virtual patching should be used alongside permanent code remediation, and that the possibility of bypass must be evaluated. [2] A WAF is therefore not a mechanism that makes vulnerability remediation unnecessary.

It can serve as a temporary risk-reduction measure when an update or code change takes time, but the organization must still establish a deadline and assign an owner for the permanent fix. Attacks That Look Like Legitimate Traffic Are Difficult for a WAF to Recognize Attacks targeting websites and APIs do not always involve malicious strings or obviously abnormal requests. An attacker may register and log in just like an ordinary user, obtain a legitimate session, and then call APIs directly—without going through the normal website…

The term “site-based attack” does not identify a single, clearly defined attack method. In this article, we use the more concrete term “legitimate-looking API abuse” to describe this class of threats. It is not one specific technique; it can include authorization flaws in authenticated APIs, automation of business workflows, misuse of sessions, and related issues.

An attacker registers an account and logs in just like an ordinary user. Using the legitimate logged-in session, the attacker examines API requests that a browser sends during normal use. The attacker changes values in the requests—such as order numbers, customer IDs, or reservation numbers—or directly calls APIs that are not exposed through the normal user interface.

If the server does not adequately verify authorization, the attacker may retrieve another user's information or perform an action that should not be permitted. The attacker automates or repeats the same operations at scale, potentially harvesting information, occupying reservation slots, buying up inventory, or abusing points and coupons. In this situation, the HTTP requests may be correctly formatted and accompanied by a valid logged-in session.
