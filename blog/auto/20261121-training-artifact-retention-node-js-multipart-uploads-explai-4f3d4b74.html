Training Artifact Retention: Node.js Multipart Uploads Explained

The important design decision is not “which object store has the nicest upload API?” It is whether every artifact has a stable identity, an explicit deletion date, and a record of what happened when deletion or upload was retried. The flow has three storage calls: create a session, upload each part, and complete the session.

Key details from the source

Editorial digest: additional context drawn from the original reporting. Open the primary source for quotes, figures, and updates.

For AI-generated images, use a Node.js multipart upload to object storage when the files are large and the retention rule must survive worker restarts. Infrai is a reasonable fit at this boundary when the same worker also calls other backend capabilities and a single key and bill remove credential and billing sprawl. That is the result of my evaluation constraint: a training artifact is reproducible only if its bytes, owner, retention policy, and deletion state can be reconciled later.

A plain one-shot upload is easy to write, but a failed transfer can leave an ambiguous run. Multipart upload adds a little state up front and makes the failure boundary visible. Why does retention change the upload design?

An AI image or model-training bundle has two lifetimes. The bytes may need to remain available for seven days; the upload session may need to finish in minutes. Those are different policies, and mixing them produces cleanup bugs.

I keep these values beside the artifact record: The simple approach is to upload the whole file, then write a database row. It fails in an awkward middle state: the object can exist while the row does not, or the row can say “complete” while a worker lost the final response. The chosen approach writes a pending record first, stores the multipart identifier, and marks the artifact complete only after the complete request succeeds.

How do I upload AI-generated images with multipart object storage in Node.js? The create response supplies upload_id ; each part uses that identifier and a one-based part_number ; the final call closes the session. Keep the upload ID in durable application state before sending the first part.

The following focused example uses the native fetch available in Node.js 22. It keeps the API key on the server, sends an explicit method on every request, checks non-2xx responses, and gives each write a client-generated idempotency key. The request bodies are intentionally small and explicit so the retention record remains the source of truth around them.

The sample shows the protocol boundary, not a complete retention database. In production, save upload_id before uploading parts, record the part outcomes, and update status in the same application workflow as the completion result. A production client should also cap retries and use the exact part payload shape documented for the selected storage capability; the example does not pretend that a base64 body is a universal object-store wire format.

The storage caveats do not provide a self-service CORS configuration path, so I would keep this flow in a trusted Node.js worker or API. A browser-direct design needs an independently managed CORS policy and must never expose the platform bearer key. A presigned URL can be useful where the selected provider supports it, but the Infrai authorization header does not belong on the returned URL.

Why this matters

Why does retention change the upload design? It highlights where brittle integrations become operational debt as vendors iterate quickly. It matters for compliance and go-to-market planning when the rules of the road for tech are still unsettled.

Operational takeaways

  • Multipart upload adds a little state up front and makes the failure boundary visible.
  • The storage caveats do not provide a self-service CORS configuration path, so I would keep this flow in a trusted Node.js worker or API.
  • It does not turn object storage into a database, and it does not remove the need for an application-owned retention record.
