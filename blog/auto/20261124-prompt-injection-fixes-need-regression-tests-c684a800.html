Prompt Injection Fixes Need Regression Tests

A patched injection could come back after, say, a model upgrade with no change to the prompt. That’s because companies build their security programs in a way that keeps security apart from delivery and doesn’t take into account the stakeholders who ship changes every week, where specialists run an adversarial review once or twice a year, patch whatever that review finds and move on.

Most engineering teams would without hesitation size up prompt injection as a security issue. That kind of cadence made some sense when it was extended from legacy systems, where code changed through planned releases and a closed hole would usually stay closed between releases. But agentic systems have changed the pace, since an agent’s behavior can now shift between two reviews without anyone touching the reviewed code.

This matters because, unlike the slow-moving threats that review cadence was built for, an agent stack keeps shifting under the patch, and a model upgrade, a prompt edit or a new data connector can reopen a gap that was closed months earlier. And so an injection that circles back after it was patched is but a regression , and catching regressions is the job test suites already do. Agent Handoffs Were Never Built to Be Suspicious Part of the reason these holes reopen is how agentic systems are wired. The output of one model becomes the input of the next. And nothing in that handoff treats what comes through with any suspicion.

Akash Agrawal , Vice President of DevOps and DevSecOps at TestMu AI , an agentic AI quality engineering platform, has worked where delivery pipelines and security controls meet, and in his current role he has spent much of his work on this failure mode. He warns that “a malicious instruction introduced into one model can propagate to others it communicates with, producing a chain reaction where compromised output becomes the next agent’s input.” The spread is hard to see from the outside, because a model can act on a poisoned…

And so problems in that traffic tend to surface in production first. In practice that means logging every message one agent passes to another and running it through the same input validation a public API endpoint would get, which gives the test suite something concrete to assert against. A Model Upgrade Could Reopen a Closed Injection Jose Lejin P J , Principal Member of Technical Staff at Salesforce, has seen fixed issues flare back from his engineering purview, going through repeated cycles of patching and retesting AI features.

And in one case, he shares, a patched injection came back through a retrieval connector that let malicious instructions ride inside a document the agent read. The instructions told the agent to disregard its guardrails along with the context from every prior step. I wrote on Techstrong.ai about RAG systems that fail upstream in the data they pull in ( https://techstrong.ai/features/rag-fails-upstream-and-most-teams-are-fixing-the-wrong-problem/ ), and an attacker who controls a single document can exploit that weakness on purpose.

Even closing the hole the first time took weeks. “This flaw was corrected by tightening the structure and processing of system prompts and inputs,” Lejin explains, “but we still observed it failing for several weeks before we finally fixed it.” The fix held until a model upgrade brought the injection straight back. “The updated version was just more compliant to the instructions found in retrieved documents, so it executed the instructions previously disregarded by the older version.

A test that replays the old attack against each new model version would have flagged it before release. For engineering teams the practical change is to treat a model version bump as a release event in its own right, logged and tested like any code change.
