My Cron Job Returns 200 When Every Fetch Fails

Layer one: an error reporter. Something pings it every 15 minutes, it fetches new jobs per category, scores them against each user's profile with Claude, and emails the good ones. The post calls this a wrong-but-working failure.

Key details from the source

Editorial digest: additional context drawn from the original reporting. Open the primary source for quotes, figures, and updates.

I wrote a post on my site about monitoring a small product without an ops team. Its strongest claim is that the worst failures are silent: no exception, no 500, just something that should have happened and did not. The layer I told people to build first was "alert on silence".

Then I did what I did with my kill switch post and opened my own repos to see if I follow my own advice. Two products: Upwork Scout, a job-alert SaaS that scans Upwork on a cron and emails matches, and VoiceDash, a white-label portal for Retell voice agents. I searched both repos for Sentry, Crashlytics, PostHog, Axiom, anything.

Six calls in Upwork Scout, twenty in VoiceDash. They go to Vercel's function logs, which I read when something already feels wrong. I am not going to pretend this is a hard problem.

The more interesting findings were in the layers below, because those are the ones where adding Sentry would not have helped at all. The cron job that succeeds at nothing Upwork Scout's whole product is one route: /api/cron/scan . One broken category should not kill the run for everyone else.

The problem is what happens when every category fails. Zero jobs means zero matches, zero emails, and then: ok: true , HTTP 200. If it is the GitHub Actions workflow in the repo, that workflow only fails when the status is not 200, so the run goes green.

Every 15 minutes, forever, a green check on a product that has stopped doing its one job. There is a smaller version of the same thing in the AI scorer. If the Claude call fails, scoreJobFit logs and returns null , and the route treats a missing verdict as "filters only": That is a deliberate degradation and I still think it is the right one: a user would rather get an unscored alert than none.

But the post says to log the decision, not just the outcome, so a correct fallback does not look like a bug. The route counts aiScored but not "AI failed, sent anyway". If the model call broke for a day, the stats would show fewer scores and more alerts, and nothing would say why.

That meta/scan write is the part that made me laugh. Every successful run stores lastRunAt and the run's stats in Firestore. It is exactly what the post tells you to build.

Operational takeaways
